# FSInfo Project Rules

Updated: 2026-09-27

1. Completed versions are immutable; every product change creates a new numbered entry and folder.
2. v0.9 is the UX Golden Master unless the owner explicitly changes the baseline.
3. One release theme at a time; unrelated ideas go to backlog.
4. Built, tested and owner-accepted are three different states. Do not advance the feature train before acceptance.
5. A regression is any new change that makes previously-good behavior worse; restore the proven behavior before expanding scope.
6. Viewport, gesture, content, Book, presentation and shell have separate state ownership; hidden dependencies are forbidden.
7. The report/book is the substantive authority; never invent missing trend prose or externally enrich by default.
8. Book content, FSInfo summaries and user assessments remain separate.
9. Major panels reserve complementary screen space; focused galaxy content must not sit behind them.
10. On mobile at most one major content bottom sheet is visible at once.
11. Presentation order: camera → narration → narration complete → trend tags → optional one-level trend presentation.
12. User pacing controls remain available: pause, previous/next, exit and reduced motion.
13. Keep the rescue core no-build/plain HTML/CSS/JS unless an approved migration changes that rule.
14. Every release gets entry HTML, sidecar prompt, numbered module folder, QA checks and a new /t/NN/ snapshot.
15. Creating a version never changes the live root; live promotion needs explicit owner approval.
16. High-state or gesture-conflicting features stay frozen until the stable core passes device and owner acceptance.
